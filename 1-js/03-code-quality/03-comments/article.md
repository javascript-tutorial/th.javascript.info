# คอมเมนต์

จากบท <info:structure> เรารู้แล้วว่าคอมเมนต์เขียนได้ 2 แบบ — บรรทัดเดียวด้วย `//` หรือหลายบรรทัดด้วย `/* ... */`

ปกติเราใช้คอมเมนต์อธิบายว่าโค้ดทำงานยังไง และทำไมถึงเขียนแบบนี้

ฟังดูง่ายใช่ไหม? แต่มือใหม่มักใช้คอมเมนต์ผิดวิธีกันอยู่บ่อยๆ

## คอมเมนต์ที่ไม่ดี

มือใหม่ชอบเขียนคอมเมนต์อธิบาย "สิ่งที่กำลังเกิดขึ้นในโค้ด" แบบนี้:

```js
// โค้ดนี้จะทำสิ่งนี้ (...) และสิ่งนั้น (...)
// ...และใครจะรู้ว่ามันยังทำอะไรอีก...
very;
complex;
code;
```

แต่ในโค้ดที่ดี คอมเมนต์แบบ "อธิบาย" นี้ควรมีน้อยที่สุด โค้ดควรอ่านเข้าใจได้เองโดยไม่ต้องพึ่งคอมเมนต์

มีกฎที่ดีมากเลย — "ถ้าโค้ดไม่ชัดจนต้องเขียนคอมเมนต์อธิบาย บางทีเขียนโค้ดใหม่น่าจะดีกว่า"

### เคล็ดลับ: แยกโค้ดออกมาเป็นฟังก์ชัน

บางครั้งการแยกส่วนหนึ่งของโค้ดออกมาเป็นฟังก์ชันก็ช่วยได้ ลองดูตัวอย่างนี้:

```js
function showPrimes(n) {
  nextPrime:
  for (let i = 2; i < n; i++) {
  
*!*
    // เช็คว่า i เป็นจำนวนเฉพาะไหม
    for (let j = 2; j < i; j++) {
      if (i % j == 0) continue nextPrime;
    }
*/!*

    alert(i);
  }
}
```

ถ้าแยกออกมาเป็นฟังก์ชัน `isPrime` จะดีกว่า:

```js
function showPrimes(n) {

  for (let i = 2; i < n; i++) {
    *!*if (!isPrime(i)) continue;*/!*

    alert(i);
  }
}

function isPrime(n) {
  for (let i = 2; i < n; i++) {
    if (n % i == 0) return false;
  }

  return true;
}
```

อ่านง่ายขึ้นเยอะเลยใช่ไหม? ตัวฟังก์ชันเองก็ทำหน้าที่เป็นคอมเมนต์ไปในตัว โค้ดแบบนี้เรียกว่า *อธิบายตัวเอง (self-descriptive)*

### เคล็ดลับ: สร้างฟังก์ชัน

ถ้าเรามี "แผ่นโค้ด" ยาวๆ แบบนี้:

```js
// ตรงนี้เติมวิสกี้
for(let i = 0; i < 10; i++) {
  let drop = getWhiskey();
  smell(drop);
  add(drop, glass);
}

// ตรงนี้เติมน้ำผลไม้ 
for(let t = 0; t < 3; t++) {
  let tomato = getTomato();
  examine(tomato);
  let juice = press(tomato);
  add(juice, glass);
}

// ...  
```

การ refactor ให้เป็นฟังก์ชันจะดีกว่า:

```js
addWhiskey(glass);
addJuice(glass);

function addWhiskey(container) {
  for(let i = 0; i < 10; i++) {
    let drop = getWhiskey();
    //...
  }
}

function addJuice(container) {
  for(let t = 0; t < 3; t++) {
    let tomato = getTomato();
    //...
  }
}  
```

เหมือนกัน — ตัวฟังก์ชันเองบอกอยู่แล้วว่าทำอะไร ไม่ต้องเขียนคอมเมนต์อธิบายเลย แถมโครงสร้างโค้ดยังดีขึ้นด้วย — เห็นชัดเจนว่าแต่ละฟังก์ชันทำอะไร รับอะไร คืนค่าอะไร

แน่นอนว่าในชีวิตจริง เราเลี่ยงคอมเมนต์แบบ "อธิบาย" ไม่ได้ทั้งหมดหรอก บางทีอัลกอริธึมซับซ้อน หรือมี "กลเม็ด" เพิ่มประสิทธิภาพโค้ด — แต่โดยทั่วไป พยายามเขียนโค้ดให้เรียบง่ายและอธิบายตัวเองได้มากที่สุดดีกว่า

## คอมเมนต์ที่ดี

เห็นแล้วว่าคอมเมนต์แบบ "อธิบายว่าทำอะไร" มักไม่ดี — แล้วแบบไหนถึงจะดีล่ะ?

อธิบายสถาปัตยกรรม
: ให้ภาพรวมของส่วนประกอบต่างๆ ว่าทำงานร่วมกันยังไง ลำดับการทำงานในแต่ละสถานการณ์เป็นแบบไหน — พูดง่ายๆ ก็คือมองโค้ดจากมุมสูงนั่นเอง มีภาษาอย่าง [UML](http://wikipedia.org/wiki/Unified_Modeling_Language) ที่ใช้วาดแผนภาพสถาปัตยกรรมอธิบายโค้ด น่าศึกษามาก

บันทึกพารามิเตอร์และวิธีใช้ฟังก์ชัน
: มีไวยากรณ์พิเศษอย่าง [JSDoc](http://en.wikipedia.org/wiki/JSDoc) สำหรับบันทึกข้อมูลฟังก์ชัน — วิธีใช้ พารามิเตอร์ และค่าที่คืนกลับมา

เช่น:
```js
/**
 * คืนค่า x ยกกำลัง n
 *
 * @param {number} x เลขที่ต้องการยกกำลัง
 * @param {number} n เลขชี้กำลัง ต้องเป็นจำนวนนับ
 * @return {number} x ยกกำลัง n
 */
function pow(x, n) {
  ...
}
```

คอมเมนต์แบบนี้ช่วยให้เข้าใจจุดประสงค์ของฟังก์ชันและใช้ได้ถูกต้อง โดยไม่ต้องไปอ่านโค้ดข้างใน

แถม editor หลายตัวอย่าง [WebStorm](https://www.jetbrains.com/webstorm/) ก็อ่านคอมเมนต์พวกนี้ได้ด้วย — เอาไปช่วยเติมโค้ดอัตโนมัติและเช็คโค้ดให้เลย

ยังมีเครื่องมืออย่าง [JSDoc 3](https://github.com/jsdoc/jsdoc) ที่สร้างเอกสาร HTML จากคอมเมนต์ได้ตรงๆ อ่านรายละเอียดเพิ่มเติมได้ที่ <https://jsdoc.app>

ทำไมถึงแก้ปัญหาด้วยวิธีนี้?
: สิ่งที่เขียนไว้สำคัญก็จริง แต่สิ่งที่ *ไม่ได้* เขียนอาจสำคัญกว่าอีก — ทำไมถึงเลือกแก้ด้วยวิธีนี้? โค้ดไม่ได้บอก

  ถ้ามีหลายวิธีแก้ปัญหา ทำไมถึงเลือกวิธีนี้ล่ะ? โดยเฉพาะถ้าไม่ใช่วิธีที่ตรงไปตรงมาที่สุด

  ถ้าไม่มีคอมเมนต์อธิบาย ก็อาจเจอสถานการณ์แบบนี้:
  1. เรา (หรือเพื่อนร่วมงาน) เปิดโค้ดที่เขียนไว้นานแล้ว แล้วรู้สึกว่า "เขียนไม่เหมาะสมเลย"
  2. คิดว่า "ตอนนั้นโง่จังเลย ตอนนี้ฉลาดขึ้นแล้ว" แล้วก็เขียนใหม่ด้วยวิธีที่ "ตรงไปตรงมาและดีกว่า"
  3. ...ความอยากเขียนใหม่เป็นเรื่องดี แต่ระหว่างทำกลับเจอว่าวิธี "ตรงไปตรงมา" ไม่ครบถ้วน พอนึกได้ลางๆ ว่าทำไมถึงเขียนแบบเดิม เพราะเคยลองมาแล้วนานมาก สุดท้ายก็เปลี่ยนกลับไปใช้วิธีเดิม — แต่เสียเวลาไปฟรีๆ

  เพราะงั้นคอมเมนต์ที่อธิบายเหตุผลของวิธีแก้ปัญหาสำคัญมาก ช่วยให้พัฒนาต่อไปในทิศทางที่ถูก

โค้ดมีจุดละเอียดอ่อนหรือเทคนิคพิเศษซ่อนอยู่ไหม? ใช้ตรงไหนบ้าง?
: ถ้าโค้ดมีอะไรที่ละเอียดอ่อนหรือขัดกับสัญชาตญาณ เขียนคอมเมนต์ไว้ให้ชัดเจนจะดีกว่า

## สรุป

สัญญาณของนักพัฒนาที่ดีคือคอมเมนต์ — ทั้งที่มีและที่ไม่มี

คอมเมนต์ที่ดีช่วยให้ดูแลโค้ดได้ดี กลับมาอ่านทีหลังก็ยังเข้าใจ และใช้งานได้ถูกต้อง

**ควรเขียนคอมเมนต์เรื่องพวกนี้:**

- สถาปัตยกรรมโดยรวม มุมมองภาพกว้าง
- วิธีใช้ฟังก์ชัน
- วิธีแก้ปัญหาที่สำคัญ โดยเฉพาะตอนที่เหตุผลไม่ได้ชัดในทันที

**อย่าเขียนคอมเมนต์แบบนี้:**

- บอกว่า "โค้ดทำงานยังไง" หรือ "ทำอะไร"
- เขียนคอมเมนต์ก็ต่อเมื่อทำโค้ดให้เรียบง่ายและอธิบายตัวเองไม่ได้จริงๆ เท่านั้น

คอมเมนต์ยังใช้กับเครื่องมือสร้างเอกสารอัตโนมัติอย่าง JSDoc3 ได้ด้วย — เครื่องมือจะอ่านคอมเมนต์แล้วสร้างเอกสาร HTML (หรือรูปแบบอื่น) ให้เลย
