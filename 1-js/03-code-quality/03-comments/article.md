# คอมเมนต์

จากบท <info:structure> เรารู้แล้วว่าคอมเมนต์เขียนได้สองแบบ คือแบบบรรทัดเดียวที่เริ่มด้วย `//` และแบบหลายบรรทัดที่อยู่ระหว่าง `/* ... */`

ปกติเราใช้คอมเมนต์อธิบายว่าโค้ดทำงานยังไง และทำไมถึงเขียนแบบนั้น

ดูเผิน ๆ การเขียนคอมเมนต์เหมือนไม่มีอะไรซับซ้อน แต่คนที่เพิ่งเริ่มเขียนโปรแกรมมักใช้ผิดจุด

## คอมเมนต์ที่ไม่ดี

มือใหม่มักเขียนคอมเมนต์เพื่อบอกว่าโค้ดกำลังทำอะไร เช่น:

```js
// โค้ดนี้ทำเรื่องนี้ (...) แล้วก็เรื่องนั้น (...)
// ...และไม่รู้ว่าทำอะไรอีกบ้าง...
very;
complex;
code;
```

แต่โค้ดที่ดีควรมีคอมเมนต์แบบนี้ให้น้อยที่สุด เพราะตัวโค้ดเองควรอ่านรู้เรื่องได้โดยไม่ต้องพึ่งคำอธิบาย

มีกฎหนึ่งที่ใช้ได้ดีมากคือ "ถ้าโค้ดอ่านไม่รู้เรื่องจนต้องมีคอมเมนต์คอยอธิบาย ลองเขียนใหม่อาจจะดีกว่า"

### วิธีหนึ่ง: แยกโค้ดออกมาเป็นฟังก์ชัน

บางครั้งแค่แยกโค้ดบางส่วนออกมาเป็นฟังก์ชันก็ทำให้อ่านง่ายขึ้น ลองดูตัวอย่างนี้:

```js
function showPrimes(n) {
  nextPrime:
  for (let i = 2; i < n; i++) {

*!*
    // ตรวจว่า i เป็นจำนวนเฉพาะหรือไม่
    for (let j = 2; j < i; j++) {
      if (i % j == 0) continue nextPrime;
    }
*/!*

    alert(i);
  }
}
```

แบบที่ดีกว่าคือแยกส่วนที่ใช้ตรวจจำนวนเฉพาะออกมาเป็นฟังก์ชัน `isPrime`:


```js
function showPrimes(n) {

  for (let i = 2; i < n; i++) {
    *!*if (!isPrime(i)) continue;*/!*

    alert(i);  
  }
}

function isPrime(n) {
  for (let i = 2; i < n; i++) {
    if (n % i == 0) return false;
  }

  return true;
}
```

ทีนี้อ่านโค้ดได้ทันทีจากชื่อฟังก์ชัน ตัวฟังก์ชันจึงทำหน้าที่แทนคอมเมนต์ โค้ดลักษณะนี้เรียกว่า *โค้ดที่อธิบายตัวเองได้ (self-descriptive)*

### อีกวิธี: สร้างฟังก์ชันให้แต่ละช่วง

ถ้ามีโค้ดยาว ๆ ที่แบ่งเป็นช่วงด้วยคอมเมนต์แบบนี้:

```js
// ตรงนี้เติมวิสกี้
for(let i = 0; i < 10; i++) {
  let drop = getWhiskey();
  smell(drop);
  add(drop, glass);
}

// ตรงนี้เติมน้ำผลไม้
for(let t = 0; t < 3; t++) {
  let tomato = getTomato();
  examine(tomato);
  let juice = press(tomato);
  add(juice, glass);
}

// ...
```

แบบที่ดีกว่าคือแยกแต่ละช่วงออกมาเป็นฟังก์ชัน:

```js
addWhiskey(glass);
addJuice(glass);

function addWhiskey(container) {
  for(let i = 0; i < 10; i++) {
    let drop = getWhiskey();
    //...
  }
}

function addJuice(container) {
  for(let t = 0; t < 3; t++) {
    let tomato = getTomato();
    //...
  }
}
```

คราวนี้ชื่อฟังก์ชันบอกเองว่าโค้ดแต่ละช่วงกำลังทำอะไร จึงไม่ต้องมีคอมเมนต์คอยกำกับ แถมโครงสร้างยังชัดขึ้น เพราะเห็นทันทีว่าแต่ละฟังก์ชันรับค่าอะไร ทำอะไร และคืนค่าอะไร

เวลาเขียนโค้ดจริง เราหลีกเลี่ยงคอมเมนต์อธิบายทั้งหมดไม่ได้ อัลกอริทึมบางอย่างซับซ้อน หรืออาจมีการปรับแต่งเฉพาะจุดเพื่อให้โค้ดทำงานเร็วขึ้น แต่โดยทั่วไปควรพยายามเขียนโค้ดให้เรียบง่ายและอธิบายตัวเองได้

## คอมเมนต์ที่ดี

เราเห็นแล้วว่าคอมเมนต์ที่คอยเล่าว่าโค้ดทำอะไรมักไม่ช่วย แล้วคอมเมนต์แบบไหนที่ควรเขียน?

อธิบายสถาปัตยกรรม
: บอกภาพรวมว่ามีส่วนประกอบอะไร ทำงานร่วมกันอย่างไร และลำดับการทำงานเปลี่ยนไปแบบไหนในแต่ละสถานการณ์ พูดง่าย ๆ คือช่วยให้มองเห็นโค้ดจากมุมสูง ภาษาอย่าง [UML](http://wikipedia.org/wiki/Unified_Modeling_Language) ใช้วาดแผนภาพสถาปัตยกรรมเพื่ออธิบายภาพรวมนี้ได้ จึงเป็นอีกเรื่องที่น่าศึกษาไว้

บันทึกพารามิเตอร์และวิธีใช้ฟังก์ชัน
: [JSDoc](http://en.wikipedia.org/wiki/JSDoc) มีรูปแบบคอมเมนต์สำหรับอธิบายวิธีใช้ พารามิเตอร์ และค่าที่ฟังก์ชันคืนมา

ตัวอย่างเช่น:
```js
/**
 * คืนค่า x ยกกำลัง n
 *
 * @param {number} x ตัวเลขที่ต้องการยกกำลัง
 * @param {number} n เลขชี้กำลัง ต้องเป็นจำนวนนับ
 * @return {number} ผลลัพธ์ของ x ยกกำลัง n
 */
function pow(x, n) {
  ...
}
```

คอมเมนต์แบบนี้ช่วยให้เข้าใจจุดประสงค์และใช้ฟังก์ชันได้ถูกต้อง โดยไม่ต้องเปิดเข้าไปอ่านโค้ดข้างใน

editor หลายตัว เช่น [WebStorm](https://www.jetbrains.com/webstorm/) อ่านคอมเมนต์รูปแบบนี้ได้ และนำข้อมูลไปช่วยเติมโค้ดอัตโนมัติและตรวจโค้ดบางส่วนได้

เครื่องมืออย่าง [JSDoc 3](https://github.com/jsdoc/jsdoc) ยังอ่านคอมเมนต์แล้วสร้างเอกสาร HTML ให้ได้ด้วย อ่านรายละเอียดเพิ่มเติมได้ที่ <https://jsdoc.app>

ทำไมต้องแก้ปัญหาด้วยวิธีนี้?
: สิ่งที่เขียนไว้ในโค้ดสำคัญ แต่สิ่งที่ *ไม่ได้* เขียนอาจสำคัญยิ่งกว่า ทำไมถึงเลือกวิธีนี้? ตัวโค้ดเองไม่ได้บอกเหตุผลไว้

    ถ้าปัญหาหนึ่งแก้ได้หลายทาง ทำไมถึงเลือกทางนี้ โดยเฉพาะเมื่อมันไม่ใช่วิธีที่ดูตรงไปตรงมาที่สุด?

    ถ้าไม่มีคอมเมนต์บอกเหตุผล อาจเกิดเหตุการณ์แบบนี้:
    1. เราหรือเพื่อนร่วมงานเปิดโค้ดที่เขียนไว้นานแล้ว และเห็นว่าวิธีเดิม "ไม่ดีเท่าที่ควร"
    2. เราคิดว่า "ตอนนั้นทำไมถึงเขียนแบบนี้ ตอนนี้รู้วิธีที่ดีกว่าแล้ว" จึงเขียนใหม่ด้วยวิธีที่ดู "ชัดกว่าและถูกกว่า"
    3. การอยากแก้โค้ดให้ดีขึ้นไม่ใช่เรื่องผิด แต่พอลงมือกลับพบว่าวิธีที่ดูชัดเจนใช้ไม่ได้อย่างที่คิด แล้วก็นึกได้ราง ๆ ว่าเคยลองวิธีนี้และเจอปัญหามาแล้ว สุดท้ายต้องย้อนกลับไปใช้วิธีเดิม เสียเวลาไปเปล่า ๆ

    คอมเมนต์ที่อธิบายเหตุผลเบื้องหลังวิธีแก้จึงสำคัญ เพราะช่วยให้พัฒนาต่อไปในทิศทางที่ถูก โดยไม่วนกลับไปติดปัญหาเดิม

โค้ดมีจุดที่คาดไม่ถึงไหม? จุดนั้นอยู่ตรงไหน?
: ถ้าโค้ดมีรายละเอียดที่เข้าใจยาก หรือมีพฤติกรรมขัดกับที่คาดไว้ ควรเขียนคอมเมนต์บอกให้ชัดเจน

## สรุป

นักพัฒนาที่ดีรู้ว่าตรงไหนควรมีคอมเมนต์ และตรงไหนไม่ควรมี

คอมเมนต์ที่ดีช่วยให้เราดูแลโค้ดได้ง่าย กลับมาอ่านทีหลังก็ยังเข้าใจ และใช้งานต่อได้ดีขึ้น

**เรื่องที่ควรเขียนคอมเมนต์:**

- สถาปัตยกรรมโดยรวมและภาพกว้างของโค้ด
- วิธีใช้ฟังก์ชัน
- เหตุผลที่เลือกวิธีแก้ปัญหาสำคัญ ๆ โดยเฉพาะเมื่ออ่านโค้ดแล้วมองไม่ออกทันที

**คอมเมนต์ที่ควรเลี่ยง:**

- คอมเมนต์ที่คอยเล่าว่าโค้ดทำงานยังไงหรือกำลังทำอะไร
- ถ้ายังปรับโค้ดให้เรียบง่ายและอธิบายตัวเองได้ ก็ควรแก้โค้ดก่อน คอมเมนต์แบบนี้ใช้เมื่อทำให้โค้ดชัดกว่านี้ไม่ได้จริง ๆ เท่านั้น
