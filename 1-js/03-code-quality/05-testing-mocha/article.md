# ทดสอบโค้ดอัตโนมัติด้วย Mocha

แบบฝึกหัดหลังจากนี้จะใช้การทดสอบอัตโนมัติอยู่เรื่อย ๆ เพราะนี่เป็นเครื่องมือพื้นฐานที่พบได้ทั่วไปในโปรเจ็กต์จริง

## ทำไมต้องเขียนเทสต์?

เวลาเขียนฟังก์ชัน เรามักรู้อยู่แล้วว่ามันควรทำอะไร เช่น ใส่พารามิเตอร์แบบไหนแล้วควรได้ผลลัพธ์อะไร

ระหว่างพัฒนา เราอาจลองเรียกฟังก์ชันในคอนโซล แล้วเทียบค่าที่ได้กับค่าที่คาดไว้

ถ้าผลไม่ถูก ก็แก้โค้ด รันใหม่ แล้วเช็กอีกครั้ง ทำซ้ำจนกว่าจะใช้ได้

ปัญหาคือการกลับมารันทดสอบด้วยมือแบบนี้มีโอกาสพลาด

**เมื่อเราทดสอบด้วยมือซ้ำ ๆ มักมีบางกรณีหลุดสายตาได้ง่าย**

สมมติว่ากำลังเขียนฟังก์ชัน `f` เราลองแล้วพบว่า `f(1)` ใช้ได้ แต่ `f(2)` พัง หลังแก้โค้ด `f(2)` ก็ทำงานแล้ว แต่เราลืมลอง `f(1)` ซ้ำ การแก้ครั้งล่าสุดจึงอาจทำให้กรณีเดิมพังโดยไม่รู้ตัว

เรื่องแบบนี้เกิดขึ้นบ่อย เพราะฟังก์ชันหนึ่งมีกรณีใช้งานให้ต้องนึกถึงหลายแบบ แต่จะให้โปรแกรมเมอร์ลองทุกกรณีใหม่ด้วยตัวเองหลังแก้โค้ดทุกครั้งคงยาก สุดท้ายเราอาจแก้จุดหนึ่งสำเร็จ แต่ทำอีกจุดพังแทน

**การทดสอบอัตโนมัติคือการเขียนโค้ดสำหรับทดสอบแยกจากโค้ดหลัก เทสต์เหล่านี้จะลองเรียกฟังก์ชันหลายรูปแบบ แล้วตรวจว่าผลลัพธ์ตรงกับที่คาดไว้หรือไม่**

## Behavior Driven Development (BDD)

เราจะเริ่มจากแนวทางที่เรียกว่า [Behavior Driven Development](http://en.wikipedia.org/wiki/Behavior-driven_development) หรือ BDD

**BDD รวมสามอย่างไว้ด้วยกัน คือเทสต์ เอกสาร และตัวอย่างการใช้งาน**

ลองดูขั้นตอนพัฒนาฟังก์ชันจริงสักตัว จะได้เห็นว่า BDD เชื่อมสามอย่างนี้เข้าด้วยกันอย่างไร

## พัฒนา "pow": เริ่มจาก spec

สมมติว่าเราต้องการฟังก์ชัน `pow(x, n)` สำหรับยก `x` กำลังจำนวนเต็ม `n` โดยกำหนดให้ `n≥0`

JavaScript มีตัวดำเนินการ `**` ที่คำนวณแบบนี้ได้อยู่แล้ว แต่ตัวอย่างนี้มีไว้พาเราดูกระบวนการพัฒนา ซึ่งนำไปใช้กับงานที่ซับซ้อนกว่านี้ได้

ก่อนลงมือเขียน `pow` เราต้องระบุให้ชัดก่อนว่าฟังก์ชันควรทำอะไร

คำอธิบายพฤติกรรมแบบนี้เรียกว่า *ข้อกำหนด (specification)* หรือเรียกสั้น ๆ ว่า spec ภายในจะบอกกรณีใช้งานต่าง ๆ พร้อมเทสต์ของแต่ละกรณี เช่น:

```js
describe("pow", function() {

  it("raises to n-th power", function() {
    assert.equal(pow(2, 3), 8);
  });

});
```

ใน spec ด้านบนมีส่วนประกอบหลัก 3 อย่าง:

`describe("title", function() { ... })`
: ระบุว่าเรากำลังอธิบายความสามารถอะไร ตัวอย่างนี้คือฟังก์ชัน `pow` และใช้รวมบล็อก `it` ที่ทดสอบแต่ละกรณีไว้เป็นกลุ่มเดียวกัน

`it("use case description", function() { ... })`
: อาร์กิวเมนต์แรกเป็นชื่อกรณีใช้งานที่คนอ่านเข้าใจได้ ส่วนอาร์กิวเมนต์ที่สองเป็นฟังก์ชันสำหรับทดสอบกรณีนั้น

`assert.equal(value1, value2)`
: ถ้าเขียนฟังก์ชัน `pow` ถูกต้อง โค้ดในบล็อก `it` ควรรันจบโดยไม่เกิด error

    ฟังก์ชันกลุ่ม `assert.*` ใช้ตรวจว่า `pow` ทำงานตรงกับที่เราคาดไว้หรือไม่ ในตัวอย่างนี้ `assert.equal` จะเปรียบเทียบอาร์กิวเมนต์สองตัว และโยน error ถ้าค่าไม่เท่ากัน จึงเป็นการตรวจว่า `pow(2, 3)` ได้ผลลัพธ์เป็น `8` จริง ส่วนรูปแบบการตรวจอื่น ๆ เราจะได้ใช้ต่อไปในบทนี้

spec เป็นโค้ดที่สั่งรันได้ เมื่อรันแล้วก็จะเรียกเทสต์ในบล็อก `it` เดี๋ยวเราจะลองทำจริงในหัวข้อถัดไป

## ขั้นตอนการพัฒนา

กระบวนการพัฒนาด้วยแนวทางนี้มักเป็นดังนี้:

1. เขียน spec ชุดแรก โดยเริ่มจากเทสต์ของความสามารถพื้นฐานที่สุด
2. เขียนโค้ดจริงฉบับแรก
3. ใช้เฟรมเวิร์กทดสอบ [Mocha](https://mochajs.org/) รัน spec ถ้าความสามารถยังไม่ครบ Mocha จะแสดง error เราก็ค่อยแก้โค้ดจนเทสต์ผ่านทั้งหมด
4. ตอนนี้เรามีโค้ดฉบับแรกที่ใช้งานได้พร้อมเทสต์
5. เพิ่มกรณีใช้งานลงใน spec โค้ดอาจยังไม่รองรับกรณีใหม่ เทสต์จึงเริ่มพัง
6. กลับไปทำข้อ 3 แล้วแก้โค้ดจนเทสต์ไม่ฟ้อง error
7. ทำข้อ 3-6 ซ้ำจนได้ความสามารถครบตามต้องการ

กระบวนการนี้จึงวนเป็นรอบ: เขียน spec เขียนโค้ดให้ใช้ได้ รันเทสต์ แล้วเพิ่มกรณีใหม่ก่อนกลับไปแก้โค้ดอีกครั้ง สุดท้ายก็จะได้ทั้งโค้ดที่ทำงานจริงและเทสต์ที่ครอบคลุมพฤติกรรมของมัน

ทีนี้มาลองเดินตามขั้นตอนนี้กับ `pow`

ขั้นแรกเสร็จแล้ว เพราะเรามี spec ชุดแรกของ `pow` อยู่ในมือ ก่อนเขียนตัวฟังก์ชัน ลองเตรียมไลบรารี JavaScript สำหรับรันเทสต์ เพื่อดูว่าระบบทำงานอย่างไร แน่นอนว่าเทสต์จะพังทั้งหมดเพราะเรายังไม่ได้เขียน `pow`

## ลองรัน spec

บทนี้ใช้ไลบรารี JavaScript สามตัวในการทดสอบ:

- [Mocha](https://mochajs.org/) — เฟรมเวิร์กหลัก มีฟังก์ชันอย่าง `describe` และ `it` รวมถึงตัวรันเทสต์
- [Chai](https://www.chaijs.com/) — ไลบรารีสำหรับตรวจผลลัพธ์ได้หลายรูปแบบ ตอนนี้เราจะใช้เพียง `assert.equal`
- [Sinon](https://sinonjs.org/) — ไลบรารีสำหรับติดตามว่าฟังก์ชันถูกเรียกอย่างไร จำลองพฤติกรรมของฟังก์ชันในตัว และงานทดสอบอื่น ๆ ซึ่งเราจะได้ใช้ในบทหลัง ๆ

ไลบรารีเหล่านี้ใช้ทดสอบได้ทั้งในเบราว์เซอร์และฝั่งเซิร์ฟเวอร์ ส่วนบทนี้จะใช้แบบเบราว์เซอร์

หน้า HTML ฉบับเต็มที่โหลดเครื่องมือทั้งหมดพร้อม spec ของ `pow` มีหน้าตาแบบนี้:

```html src="index.html"
```

แบ่งหน้าออกได้เป็น 5 ส่วน:

1. `<head>` โหลดไลบรารีจากภายนอกและสไตล์สำหรับแสดงผลเทสต์
2. `<script>` ใส่ฟังก์ชันที่ต้องการทดสอบ ซึ่งในที่นี้คือ `pow`

4. Mocha ใช้ `<div id="mocha">` แสดงผลลัพธ์
5. คำสั่ง `mocha.run()` เริ่มรันเทสต์

## เติมกรณีให้ spec

แต่เห็นชัดว่าเราโกง เพราะฟังก์ชันยังคำนวณจริงไม่ได้ ถ้าลอง `pow(3,4)` จะได้คำตอบผิด ทั้งที่เทสต์ยังผ่าน

เหตุการณ์แบบนี้เกิดขึ้นในงานจริงได้ เทสต์ผ่านแต่ฟังก์ชันทำงานผิด แปลว่า spec ของเรายังมีกรณีไม่ครบ

ลองเพิ่มเทสต์ที่ตรวจว่า `pow(3, 4) = 81`

จัดเทสต์ได้สองแบบ:

1. เพิ่ม `assert` อีกตัวลงใน `it` เดิม:

    ```js
    describe("pow", function() {

      it("raises to n-th power", function() {
        assert.equal(pow(2, 3), 8);
    *!*
        assert.equal(pow(3, 4), 81);
    */!*
      });

    });
    ```
2. แยกเป็นสองเทสต์:

    ```js
    describe("pow", function() {

      it("2 raised to power 3 is 8", function() {
        assert.equal(pow(2, 3), 8);
      });

      it("3 raised to power 4 is 81", function() {
        assert.equal(pow(3, 4), 81);
      });

    });
    ```

ความต่างสำคัญคือ เมื่อ `assert` เจอ error บล็อก `it` จะหยุดทำงานทันที ถ้าใช้แบบแรกแล้ว `assert` ตัวแรกพัง เราจะไม่เห็นผลของตัวที่สองเลย

การแยกแต่ละกรณีเป็นคนละเทสต์จึงบอกเราได้ชัดกว่าว่าเกิดอะไรขึ้น แบบที่สองเลยเหมาะกว่า

มีกฎสั้น ๆ ที่ควรจำไว้ด้วย:

**หนึ่งเทสต์ควรตรวจแค่เรื่องเดียว**

ถ้าในเทสต์เดียวมีการตรวจสองเรื่องที่ไม่เกี่ยวกัน ควรแยกออกเป็นสองเทสต์ย่อย

## ปรับฟังก์ชันให้ทำงานจริง

คราวนี้เขียน `pow` ให้คำนวณจริงเพื่อให้เทสต์ผ่าน:

```js
function pow(x, n) {
  let result = 1;

  for (let i = 0; i < n; i++) {
    result *= x;
  }

  return result;
}
```

เพื่อให้มั่นใจขึ้น ลองทดสอบค่าหลาย ๆ ค่า แทนที่จะเขียนบล็อก `it` ทีละตัว เราใช้ `for` สร้างเทสต์ได้:

```js
describe("pow", function() {

  function makeTest(x) {
    let expected = x * x * x;
    it(`${x} in the power 3 is ${expected}`, function() {
      assert.equal(pow(x, 3), expected);
    });
  }

  for (let x = 1; x <= 5; x++) {
    makeTest(x);
  }

});
```

## ซ้อน describe เพื่อจัดกลุ่มเทสต์

เราจะเพิ่มเทสต์อีกหลายกรณี แต่ก่อนอื่นควรจัดฟังก์ชันตัวช่วย `makeTest` กับลูป `for` ไว้ด้วยกัน `makeTest` ไม่ได้ใช้ในเทสต์อื่น มีไว้ให้ลูป `for` เรียกเพื่อสร้างชุดทดสอบการยกกำลังสามเท่านั้น

เราใช้ `describe` ซ้อนอีกชั้นเพื่อรวมส่วนนี้เป็นกลุ่มเดียวกันได้:

```js
describe("pow", function() {

*!*
  describe("raises x to power 3", function() {
*/!*

    function makeTest(x) {
      let expected = x * x * x;
      it(`${x} in the power 3 is ${expected}`, function() {
        assert.equal(pow(x, 3), expected);
      });
    }

    for (let x = 1; x <= 5; x++) {
      makeTest(x);
    }

*!*
  });
*/!*

  // ... เพิ่มเทสต์อื่นต่อจากนี้ได้ ทั้ง describe และ it
});
```

`describe` ที่ซ้อนอยู่จะสร้างกลุ่มย่อยของเทสต์ ตอนแสดงผลจึงเห็นชื่อกลุ่มนี้เยื้องเข้าไปอีกระดับ:

[iframe height=250 src="pow-4" edit border="1"]

หลังจากนี้เราเพิ่ม `it` หรือ `describe` อื่นในระดับบนสุดได้ แต่ละกลุ่มก็มีฟังก์ชันตัวช่วยของตัวเองได้ โดยโค้ดเหล่านั้นจะมองไม่เห็น `makeTest` ที่อยู่ในกลุ่มนี้

````smart header="`before/after` และ `beforeEach/afterEach`"
ฟังก์ชัน `before/after` ใช้รันโค้ดก่อน/หลังเทสต์ทั้งหมด ส่วน `beforeEach/afterEach` ใช้รันโค้ดก่อน/หลังบล็อก `it` *ทุกบล็อก*

ตัวอย่าง:

```js no-beautify
describe("test", function() {

  before(() => alert("Testing started – before all tests"));
  after(() => alert("Testing finished – after all tests"));

  beforeEach(() => alert("Before a test – enter a test"));
  afterEach(() => alert("After a test – exit a test"));

  it('test 1', () => alert(1));
  it('test 2', () => alert(2));

});
```

โค้ดจะทำงานตามลำดับนี้:

```
Testing started – before all tests (before)
Before a test – enter a test (beforeEach)
1
After a test – exit a test   (afterEach)
Before a test – enter a test (beforeEach)
2
After a test – exit a test   (afterEach)
Testing finished – after all tests (after)
```

[edit src="beforeafter" title="เปิดตัวอย่างใน sandbox"]

โดยทั่วไป `beforeEach/afterEach` และ `before/after` ใช้เตรียมข้อมูลตั้งต้น รีเซ็ตตัวนับ หรือทำงานอื่นที่ต้องเกิดขึ้นระหว่างเทสต์หรือกลุ่มเทสต์
````

## ขยาย spec ให้ครบขึ้น

ความสามารถพื้นฐานของ `pow` เสร็จแล้ว เท่ากับจบรอบแรกของการพัฒนา ฉลองรอบแรกกันพอแล้ว ไปเพิ่มความสามารถต่อ

เรากำหนดไว้ว่า `pow(x, n)` ต้องรับ `n` เป็นจำนวนเต็มที่ไม่ติดลบ

เมื่อเกิดข้อผิดพลาดทางคณิตศาสตร์ ฟังก์ชัน JavaScript มักคืนค่า `NaN` เราจะให้ `pow` ทำแบบเดียวกันเมื่อได้รับ `n` ที่ใช้ไม่ได้

ตามแนวทาง BDD เราเพิ่มพฤติกรรมนี้ลงใน spec ก่อน:

```js
describe("pow", function() {

  // ...

  it("for negative n the result is NaN", function() {
*!*
    assert.isNaN(pow(2, -1));
*/!*
  });

  it("for non-integer n the result is NaN", function() {
*!*
    assert.isNaN(pow(2, 1.5));    
*/!*
  });

});
```

```smart header="วิธีตรวจค่าแบบอื่น"

```js
function pow(x, n) {
*!*
  if (n < 0) return NaN;
  if (Math.round(n) != n) return NaN;
*/!*

  let result = 1;

  for (let i = 0; i < n; i++) {
    result *= x;
  }

  return result;
}
```

## สรุป

ใน BDD เราเขียน spec ก่อน แล้วจึงเขียนโค้ดให้ทำงานตาม spec สุดท้ายจึงได้ทั้งข้อกำหนดและโค้ดจริง

เรานำ spec ชุดเดียวไปใช้ได้ 3 ทาง:

1. เป็น **เทสต์** ช่วยยืนยันว่าโค้ดทำงานถูกต้อง
2. เป็น **เอกสาร** เพราะชื่อของ `describe` และ `it` บอกว่าฟังก์ชันทำอะไร
3. เป็น **ตัวอย่าง** เพราะแต่ละเทสต์คือโค้ดที่รันได้จริงและแสดงวิธีเรียกใช้ฟังก์ชัน

เมื่อมี spec คอยตรวจ เราปรับ แก้ หรือเขียนฟังก์ชันใหม่ทั้งตัวได้โดยยังเช็กได้ว่าพฤติกรรมเดิมทำงานถูกต้อง

จุดนี้สำคัญมากในโปรเจ็กต์ใหญ่ที่ฟังก์ชันหนึ่งถูกเรียกจากหลายแห่ง เพราะหลังแก้ฟังก์ชัน เราแทบไม่มีทางลองทุกจุดที่เรียกใช้ด้วยมือให้ครบได้

ถ้าไม่มีเทสต์ มักเหลือสองทางเลือก:

1. แก้โค้ดไปก่อนแล้วเสี่ยงให้ผู้ใช้เจอบั๊ก เพราะเราตรวจด้วยมือไม่ครบ
2. ถ้าความผิดพลาดมีผลร้ายแรง ทุกคนก็จะกลัวการแก้ฟังก์ชันนั้น โค้ดจึงค่อย ๆ ล้าสมัยและไม่มีใครอยากแตะ ซึ่งไม่เป็นผลดีกับการพัฒนา

**การทดสอบอัตโนมัติช่วยลดปัญหาเหล่านี้ได้**

เมื่อโปรเจ็กต์มีเทสต์ครอบคลุม หลังแก้โค้ดเราสั่งรันครั้งเดียวก็ตรวจกรณีต่าง ๆ จำนวนมากได้ในไม่กี่วินาที

**โค้ดที่ทดสอบได้ดียังมักมีโครงสร้างที่ดีขึ้นด้วย**

เหตุผลหนึ่งคือโค้ดที่มีเทสต์ปรับปรุงและแก้ไขได้ง่าย อีกเหตุผลคือการจะเขียนเทสต์ได้ เราต้องจัดให้แต่ละฟังก์ชันมีหน้าที่ชัดเจน รวมถึงกำหนดอินพุตและผลลัพธ์ให้แน่นอน โครงสร้างของโปรแกรมจึงมีแนวโน้มดีตั้งแต่ต้น

แน่นอนว่างานจริงไม่ได้ง่ายแบบนี้เสมอไป บางครั้งเรายังเขียน spec ก่อนโค้ดไม่ได้ เพราะยังไม่ชัดว่าฟังก์ชันควรทำงานอย่างไร แต่โดยรวมแล้ว เทสต์ช่วยให้พัฒนาได้เร็วและมั่นคงขึ้น

ในบทถัด ๆ ไปจะมีแบบฝึกหัดที่เตรียมเทสต์ไว้ให้ เราจึงได้เห็นตัวอย่างการใช้งานจริงมากขึ้น

การเขียนเทสต์ต้องอาศัยความรู้ JavaScript พอสมควร แต่ตอนนี้เราเพิ่งเริ่มเรียน จึงยังไม่จำเป็นต้องเขียนเทสต์เอง ขอแค่อ่านเทสต์ออก แม้เทสต์นั้นจะซับซ้อนกว่าตัวอย่างในบทนี้เล็กน้อยก็พอ
