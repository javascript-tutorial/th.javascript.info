# โค้ดนินจา


```quote author="ขงจื๊อ (คัมภีร์หลุนอี่ว์)"
เรียนโดยไม่คิดก็เหนื่อยเปล่า คิดโดยไม่เรียนก็อันตราย
```

โปรแกรมเมอร์นินจาในอดีตใช้กลเม็ดเหล่านี้ลับสมองคนที่ต้องมาดูแลโค้ดต่อ

เหล่าปรมาจารย์ด้านการรีวิวโค้ดก็มักมองหากลเม็ดพวกนี้เวลาอ่านโค้ดจากโจทย์ทดสอบ

บางครั้งนักพัฒนามือใหม่กลับใช้ได้คล่องยิ่งกว่านินจาโปรแกรมเมอร์เสียอีก

อ่านให้ดี แล้วลองดูว่าตัวเองเป็นใคร — นินจา มือใหม่ หรืออาจเป็นคนรีวิวโค้ด?


```warn header="ตรวจพบคำประชด"
หลายคนพยายามเดินตามวิถีนินจา แต่มีน้อยคนที่จะทำสำเร็จ
```


## สั้นไว้ก่อน จะได้ดูฉลาด

เขียนโค้ดให้สั้นที่สุด โชว์ให้ทุกคนเห็นว่าเราเก่งแค่ไหน

ปล่อยให้ลูกเล่นชวนงงของภาษาเป็นตัวนำทาง

อย่างตัวดำเนินการแบบมีเงื่อนไข `'?'` บรรทัดนี้:

```js
// นำมาจากไลบรารี JavaScript ชื่อดัง
i = i ? i < 0 ? Math.max(0, len + i) : i : 0;
```

เท่ใช่ไหม? ถ้าเขียนแบบนี้ นักพัฒนาที่มาเจอบรรทัดนี้แล้วพยายามหาว่า `i` มีค่าอะไรจะได้สนุกเต็มที่ สุดท้ายก็ต้องเดินมาถามเราอยู่ดี

บอกเขาไปว่าโค้ดยิ่งสั้นยิ่งดี แล้วรับเข้าสู่วิถีนินจาเสียเลย

## ตัวแปรชื่อหนึ่งตัวอักษร

```quote author="เล่าจื๊อ (เต๋าเต๋อจิง)"
เต๋าซ่อนอยู่ในความไร้ถ้อยคำ มีเพียงเต๋าที่เริ่มต้นและจบลงได้อย่างสมบูรณ์
```

อีกวิธีที่จะทำให้โค้ดสั้นลงคือใช้ชื่อตัวแปรตัวอักษรเดียวทุกที่ เช่น `a`, `b` หรือ `c`

ชื่อสั้น ๆ จะกลืนหายไปในโค้ดเหมือนนินจาหายเข้าไปในป่า ไม่มีใครตามหาเจอด้วยฟังก์ชันค้นหาของ editor ต่อให้เจอ ก็มองไม่ออกอยู่ดีว่า `a` หรือ `b` หมายถึงอะไร

แต่มีข้อยกเว้น นินจาตัวจริงจะไม่ใช้ `i` เป็นตัวนับในลูป `"for"` เด็ดขาด ที่อื่นใช้ได้ แต่ตรงนี้ห้าม ลองเลือกตัวอักษรแปลกตากว่านั้น เช่น `x` หรือ `y`

การใช้ตัวอักษรแปลกตาเป็นตัวนับจะยิ่งดูดี ถ้าโค้ดในลูปยาวหนึ่งหรือสองหน้า ถ้าทำให้ยาวกว่านั้นได้ก็เอาเลย ใครที่เปิดมาอ่านช่วงกลางลูปจะได้มองไม่ออกว่า `x` คือตัวนับของลูป

## ใช้คำย่อ

ถ้ากฎของทีมห้ามใช้ชื่อที่มีตัวอักษรเดียวหรือชื่อที่คลุมเครือ ก็ย่อชื่อให้กลายเป็นคำย่อแทน

เช่น:

- `list` -> `lst`
- `userAgent` -> `ua`
- `browser` -> `brsr`
- ...และอื่น ๆ

มีแต่คนที่สัญชาตญาณแม่นจริง ๆ เท่านั้นถึงจะอ่านชื่อเหล่านี้ออก พยายามย่อทุกอย่างเข้าไว้ เพราะคนที่จะมาดูแลโค้ดของเราต่อต้องเป็นผู้ที่คู่ควรเท่านั้น

## ทะยานให้สูง ตั้งชื่อให้เป็นนามธรรม

```quote author="เล่าจื๊อ (เต๋าเต๋อจิง)"
สี่เหลี่ยมที่ยิ่งใหญ่ไร้มุม<br>
ภาชนะที่ยิ่งใหญ่เสร็จสมบูรณ์ช้าที่สุด<br>
เสียงที่ยิ่งใหญ่เบาบางจนแทบไม่ได้ยิน<br>
ภาพที่ยิ่งใหญ่ไร้รูปทรง
```

เวลาเลือกชื่อ ให้ใช้คำที่เป็นนามธรรมที่สุด เช่น `obj`, `data`, `value`, `item`, `elem` และคำทำนองนี้

- **ชื่อตัวแปรที่สมบูรณ์แบบคือ `data`** ใช้ทุกที่ที่ใช้ได้ เพราะตัวแปรทุกตัวก็เก็บ *ข้อมูล* ไม่ใช่หรือ?

    แล้วถ้า `data` ถูกใช้ไปแล้วล่ะ? ลอง `value` ดู คำนี้ใช้ได้ครอบจักรวาลเหมือนกัน เพราะสุดท้ายตัวแปรก็ต้องมี *ค่า*

- **ตั้งชื่อตัวแปรตามชนิดของมัน เช่น `str`, `num`...**

    ลองใช้ดู ศิษย์รุ่นใหม่อาจสงสัยว่าชื่อแบบนี้มีประโยชน์กับนินจาจริงหรือ แน่นอนว่ามี!

    ชื่อตัวแปรยังพอบอกได้ว่าข้างในเป็นสตริง ตัวเลข หรือค่าแบบอื่น แต่พอคนนอกพยายามทำความเข้าใจโค้ด เขาจะต้องประหลาดใจ เพราะชื่อเหล่านี้ไม่ได้บอกข้อมูลที่จำเป็นเลย สุดท้ายก็แก้โค้ดที่เราคิดมาอย่างรอบคอบไม่ได้

    เราหาชนิดของค่าได้ง่าย ๆ ด้วยการดีบัก แต่ความหมายของตัวแปรล่ะ? มันเก็บสตริงอะไร หรือตัวเลขอะไร?

    ถ้าไม่นั่งสมาธิให้ดี ก็ไม่มีทางรู้ได้เลย

- **แล้วถ้าชื่อพวกนี้ถูกใช้หมดแล้วล่ะ?** แค่เติมตัวเลขต่อท้าย: `data1, item2, elem5`...

## ทดสอบความใส่ใจ

มีแต่โปรแกรมเมอร์ที่ใส่ใจจริง ๆ เท่านั้นที่ควรอ่านโค้ดของเราออก แล้วจะทดสอบได้อย่างไร?

**วิธีหนึ่งคือใช้ชื่อตัวแปรที่คล้ายกัน เช่น `date` กับ `data`**

สลับสองชื่อนี้ไปมาให้ทั่วโค้ด

เพียงเท่านี้ก็กวาดตาอ่านเร็ว ๆ ไม่ได้แล้ว ถ้าพิมพ์ผิดขึ้นมาอีกสักจุด ก็คงติดอยู่ตรงนั้นกันอีกนาน ได้เวลาพักไปชงชา


## คำพ้องแสนฉลาด

```quote author="เล่าจื๊อ (เต๋าเต๋อจิง)"
เต๋าที่เอ่ยออกมาได้ไม่ใช่เต๋าอันเป็นนิรันดร์ นามที่เรียกขานได้ไม่ใช่นามอันเป็นนิรันดร์
```

การใช้ชื่อ *คล้ายกัน* กับสิ่งที่ *เหมือนกัน* ช่วยให้ชีวิตน่าสนใจขึ้น แถมยังได้แสดงความคิดสร้างสรรค์ให้ทุกคนเห็น

ลองดูคำนำหน้าชื่อฟังก์ชัน ถ้าฟังก์ชันแสดงข้อความบนหน้าจอ ให้ขึ้นต้นด้วย `display…` เช่น `displayMessage` แต่ถ้าอีกฟังก์ชันแสดงอย่างอื่นบนหน้าจอ เช่นชื่อผู้ใช้ ก็ให้ขึ้นต้นด้วย `show…` อย่าง `showName`

ชวนให้คนอ่านคิดว่าฟังก์ชันสองแบบนี้มีความต่างเล็ก ๆ ซ่อนอยู่ ทั้งที่จริงแล้วไม่ต่างกันเลย

นัดแนะกับเพื่อนนินจาในทีมไว้ด้วย ถ้าจอห์นใช้ `display...` กับฟังก์ชันแสดงผลในโค้ดของเขา ปีเตอร์ก็ใช้ `render..` ส่วนแอนใช้ `paint...` สังเกตไหมว่าโค้ดดูน่าสนใจและหลากหลายขึ้นมาก

ทีนี้มาถึงไม้เด็ด

ฟังก์ชันสองตัวที่ทำงานต่างกันคนละเรื่อง ให้ใช้คำนำหน้าเดียวกัน!

เช่น ฟังก์ชัน `printPage(page)` จะส่งหน้าไปยังเครื่องพิมพ์ ส่วน `printText(text)` จะแสดงข้อความบนหน้าจอ ปล่อยให้คนที่ไม่คุ้นกับโค้ดนั่งคิดหนักว่า `printMessage` จะส่งข้อความไปไหน เครื่องพิมพ์หรือหน้าจอ? ถ้าอยากให้เด็ดจริง `printMessage(message)` ควรแสดงข้อความในหน้าต่างใหม่

## ใช้ชื่อซ้ำ

```quote author="เล่าจื๊อ (เต๋าเต๋อจิง)"
เมื่อสิ่งที่เป็นหนึ่งถูกแบ่งออก แต่ละส่วน<br>
ย่อมต้องมีชื่อ<br>
ชื่อที่มีอยู่ก็มากพอแล้ว<br>
จึงต้องรู้ว่าเมื่อใดควรหยุด
```

เพิ่มตัวแปรใหม่เมื่อจำเป็นจริง ๆ เท่านั้น

นอกนั้นให้ใช้ชื่อที่มีอยู่ซ้ำ แล้วเขียนค่าใหม่ทับลงไป

ในฟังก์ชัน พยายามใช้เฉพาะตัวแปรที่รับเข้ามาทางพารามิเตอร์

คนอ่านจะได้ตามยากว่าตัวแปรเก็บอะไรอยู่ *ในตอนนี้* และค่านั้นมาจากไหน จุดประสงค์คือฝึกสัญชาตญาณกับความจำของคนอ่านโค้ด คนที่สัญชาตญาณไม่ดีพอจะต้องไล่อ่านทีละบรรทัดและตามดูค่าที่เปลี่ยนไปในทุกทางแยกของโค้ด

**ขั้นสูงกว่านั้นคือแอบ (!) เปลี่ยนค่าเป็นอีกค่าที่ดูคล้ายกันตรงกลางลูปหรือกลางฟังก์ชัน**

เช่น:

```js
function ninjaFunction(elem) {
  // โค้ด 20 บรรทัดที่ทำงานกับ elem

  elem = clone(elem);

  // อีก 20 บรรทัด ซึ่งคราวนี้ทำงานกับสำเนาของ elem!
}
```

เพื่อนร่วมทีมที่อยากใช้ `elem` ในช่วงครึ่งหลังของฟังก์ชันจะต้องแปลกใจ กว่าจะรู้ว่ากำลังทำงานกับสำเนาอยู่ก็ต้องเปิดดีบักเกอร์และไล่อ่านโค้ด

กลเม็ดนี้เจอเป็นประจำในโค้ดจริง และได้ผลร้ายแรงแม้แต่กับนินจามากประสบการณ์

## ใส่ขีดล่างให้สนุก

เติมขีดล่าง (underscore) `_` และ `__` ไว้หน้าชื่อตัวแปร เช่น `_name` หรือ `__value` จะดีที่สุดถ้ามีแค่เราที่รู้ความหมาย หรือจะให้ดีกว่านั้นก็ใส่ไว้เล่น ๆ โดยไม่ต้องมีความหมายเลย จะใช้คนละความหมายในแต่ละจุดก็ได้

เท่ากับยิงปืนนัดเดียวได้นกสองตัว อย่างแรก โค้ดยาวขึ้นและอ่านยากขึ้น อย่างที่สอง เพื่อนนักพัฒนาอาจเสียเวลาอยู่นานเพื่อหาว่าขีดล่างเหล่านั้นหมายถึงอะไร

นินจาที่ฉลาดจะใส่ขีดล่างในโค้ดบางจุดแล้วไม่ใส่ในจุดอื่น ความไม่สม่ำเสมอนี้ทำให้โค้ดเปราะบางขึ้นและเพิ่มโอกาสเกิดข้อผิดพลาดในอนาคต

## แสดงความรัก

ทำให้ทุกคนเห็นว่าสิ่งที่เราสร้างยิ่งใหญ่แค่ไหน ชื่ออย่าง `superElement`, `megaFrame` และ `niceItem` จะช่วยให้คนอ่านตาสว่างแน่นอน

คำว่า `super..`, `mega..`, `nice..` ฟังดูเหมือนจะบอกอะไรสักอย่าง แต่จริง ๆ แล้วไม่ได้ให้รายละเอียดเลย คนอ่านอาจคิดว่ามีความหมายซ่อนอยู่ แล้วใช้เวลางานหนึ่งหรือสองชั่วโมงนั่งทำสมาธิค้นหาความหมายนั้น


## ตั้งชื่อทับตัวแปรด้านนอก

```quote author="กวนอินจื้อ"
เมื่ออยู่ในแสงสว่าง ย่อมมองไม่เห็นสิ่งใดในความมืด<br>
เมื่ออยู่ในความมืด ย่อมมองเห็นทุกสิ่งในแสงสว่าง
```

ใช้ชื่อเดียวกันกับตัวแปรทั้งข้างในและข้างนอกฟังก์ชัน ง่าย ๆ แค่นั้น ไม่ต้องเสียแรงคิดชื่อใหม่

```js
let *!*user*/!* = authenticateUser();

function render() {
  let *!*user*/!* = anotherValue();
  ...
  ...many lines...
  ...
  ... // <-- โปรแกรมเมอร์อยากใช้ user ตรงนี้ แล้วก็...
  ...
}
```

โปรแกรมเมอร์ที่เปิดมาอ่านกลางฟังก์ชัน `render` อาจไม่ทันสังเกตว่ามี `user` ภายในฟังก์ชันบังตัวแปรชื่อเดียวกันที่อยู่ข้างนอก

จากนั้นก็จะใช้ `user` โดยคิดว่าเป็นตัวแปรภายนอกซึ่งได้มาจาก `authenticateUser()` กับดักทำงานแล้ว ถึงเวลาเปิดดีบักเกอร์


## ใส่ผลข้างเคียงได้ทุกที่!

ฟังก์ชันบางตัวดูเหมือนจะไม่เปลี่ยนแปลงอะไร เช่น `isReady()`, `checkPermission()`, `findTags()`... คนอ่านย่อมคาดว่าฟังก์ชันเหล่านี้มีหน้าที่คำนวณ ค้นหา และคืนข้อมูล โดยไม่เปลี่ยนสิ่งใดที่อยู่นอกฟังก์ชัน หรือพูดอีกอย่างว่าไม่มี "ผลข้างเคียง"

**กลเม็ดที่งดงามจริง ๆ คือเพิ่มการกระทำที่ "มีประโยชน์" เข้าไป นอกเหนือจากงานหลักของฟังก์ชัน**

สีหน้างุนงงของเพื่อนร่วมงานเมื่อเห็นฟังก์ชันชื่อ `is..`, `check..` หรือ `find...` เปลี่ยนค่าอะไรบางอย่าง จะช่วยเปิดโลกทางความคิดให้เขาแน่นอน

**อีกวิธีสร้างความประหลาดใจคือคืนผลลัพธ์ที่คนอ่านคาดไม่ถึง**

โชว์ความคิดไม่เหมือนใครเสียหน่อย ให้ `checkPermission` คืนค่าเป็นออบเจ็กต์ซับซ้อนที่เก็บผลการตรวจ แทนที่จะคืน `true/false`

นักพัฒนาที่ลองเขียน `if (checkPermission(..))` จะสงสัยว่าทำไมถึงใช้ไม่ได้ บอกเขาไปว่า "อ่านเอกสารสิ!" แล้วส่งบทความนี้ให้

```quote author="เล่าจื๊อ (เต๋าเต๋อจิง)"
ทั้งทางซ้ายและทางขวา
```

อย่าจำกัดฟังก์ชันให้ทำแค่งานตามชื่อ มองให้กว้างกว่านั้น

เช่น ฟังก์ชัน `validateEmail(email)` อาจตรวจความถูกต้องของอีเมล พร้อมกับแสดงข้อความ error และขอให้ผู้ใช้กรอกอีเมลใหม่

ชื่อฟังก์ชันต้องไม่บอกใบ้ว่ามีงานแถมเหล่านี้ และนินจาตัวจริงจะทำให้มองไม่ออกจากโค้ดด้วย

**การรวมงานหลายอย่างไว้ด้วยกันจะปกป้องโค้ดของเราจากการนำกลับไปใช้ซ้ำ**

ลองนึกว่านักพัฒนาอีกคนต้องการแค่ตรวจอีเมลโดยไม่แสดงข้อความ ฟังก์ชัน `validateEmail(email)` ของเราที่ทำทั้งสองอย่างก็ไม่ตอบโจทย์ แบบนี้เขาก็จะไม่มาถามอะไรให้เสียสมาธิของเรา

## สรุป

"คำแนะนำ" ทุกข้อข้างบนมาจากโค้ดจริง บางครั้งเขียนโดยนักพัฒนาที่มีประสบการณ์มากกว่าเราด้วยซ้ำ ;)

- ทำตามบางข้อ โค้ดจะเต็มไปด้วยเรื่องน่าประหลาดใจ
- ทำตามหลายข้อ โค้ดจะกลายเป็นของเราอย่างแท้จริง เพราะไม่มีใครอยากแก้
- ทำตามทุกข้อ โค้ดจะกลายเป็นบทเรียนล้ำค่าสำหรับนักพัฒนารุ่นใหม่ที่กำลังแสวงหาการรู้แจ้ง
