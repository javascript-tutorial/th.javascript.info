# โค้ดนินจา

```quote author="ขงจื๊อ (วจนะ)"
เรียนไร้คิดเหนื่อยเปล่าดุจดั่งฝัน คิดไร้เรียนอันตรายใช่น้อยเลย
```

โปรแกรมเมอร์นินจาในอดีตใช้กลเม็ดพวกนี้ลับสมองผู้ดูแลโค้ด

ผู้เชี่ยวชาญการรีวิวโค้ดก็มองหากลเม็ดพวกนี้เวลาทดสอบงาน

บางครั้งมือใหม่เล่นกลเม็ดพวกนี้ได้ดีกว่าโปรแกรมเมอร์นินจาด้วยซ้ำ

ลองอ่านดูให้ดี แล้วถามตัวเองว่าเราเป็นใคร — นินจา มือใหม่ หรือผู้รีวิวโค้ด?

```warn header="พบการเสียดสี"
มากมายมุ่งวิถีนินจา น้อยนักล่วงพ้นถึงจุดหมาย
```

## ความกระชับคือหัวใจของปัญญา

เขียนโค้ดให้สั้นที่สุดเท่าที่จะทำได้ โชว์ความฉลาดให้โลกเห็น

ปล่อยให้ฟีเจอร์ลึกลับของภาษาเป็นตัวนำทาง

เช่น ลองดู ternary operator `'?'` นี้:

```js
// มาจากไลบรารี JavaScript ที่มีชื่อเสียง
i = i ? i < 0 ? Math.max(0, len + i) : i : 0;
```

เจ๋งใช่ไหม? ถ้าเขียนแบบนี้ นักพัฒนาที่เจอบรรทัดนี้แล้วพยายามไล่ดูว่า `i` มีค่าเท่าไหร่คงสนุกกันน่าดู ท้ายที่สุดก็ต้องมาถามเราเพื่อขอคำตอบนั่นแหละ

บอกไปเลยว่าสั้นกว่าดีกว่าเสมอ แล้วชี้ทางพวกเขาไปสู่วิถีแห่งนินจา

## ตัวแปรตัวอักษรเดียว

```quote author="เล่าจื๊อ (เต๋าเต๋อจิง)"
เต๋าซ่อนในความเงียบไร้คำ เริ่มต้นและจบลงอย่างสมบูรณ์
```

อีกท่าในการเขียนโค้ดให้สั้นลงคือใช้ชื่อตัวแปรตัวอักษรเดียวทุกที่ เช่น `a`, `b` หรือ `c`

ตัวแปรที่สั้นจะหายไปในโค้ดเหมือนนินจาหายเข้าป่า ไม่มีใครหาเจอด้วยฟีเจอร์ "ค้นหา" ของ editor ถึงจะเจอก็ "ถอดรหัส" ไม่ออกว่า `a` หรือ `b` หมายถึงอะไร

...แต่มีข้อยกเว้น — นินจาตัวจริงจะไม่มีวันใช้ `i` เป็นตัวนับในลูป `"for"` ที่ไหนก็ใช้ได้ แต่ไม่ใช่ตรงนี้ ลองมองหารอบๆ ดูสิ มีตัวอักษรแปลกๆ อีกเพียบ เช่น `x` หรือ `y`

ใช้ตัวแปรแปลกๆ เป็นตัวนับลูปนี่เจ๋งสุดๆ โดยเฉพาะถ้าในลูปยาว 1-2 หน้า (ยิ่งยาวยิ่งดี) เพราะถ้ามีใครมาไล่ดูโค้ดข้างในลูป จะเดาไม่ออกเลยว่า `x` คือตัวนับลูปนั่นเอง


## ใช้คำย่อ

ถ้ากฎของทีมห้ามใช้ชื่อตัวอักษรเดียวหรือชื่อคลุมเครือ — ก็ย่อมันซะ สร้างคำย่อขึ้นมา

แบบนี้:

- `list` -> `lst`
- `userAgent` -> `ua`
- `browser` -> `brsr` 
- ...ฯลฯ

คนที่สัญชาตญาณดีเยี่ยมเท่านั้นถึงจะเข้าใจชื่อแบบนี้ได้ พยายามย่อทุกอย่างเลย มีแต่คนที่คู่ควรเท่านั้นแหละที่จะดูแลโค้ดของเราต่อได้

## โบยบินสูงส่ง ดั่งนามธรรม

```quote author="เล่าจื๊อ (เต๋าเต๋อจิง)"
สี่เหลี่ยมใหญ่ไร้มุมแหลมคม
ภาชนะยิ่งใหญ่เสร็จสิ้นท้ายสุด
เสียงอันไพเราะคือความเบาบาง
ภาพอันยิ่งใหญ่ไร้รูปทรง
```

ตอนตั้งชื่อ เลือกคำที่เป็นนามธรรมที่สุด เช่น `obj`, `data`, `value`, `item`, `elem` เป็นต้น

- **`data` คือชื่อตัวแปรในอุดมคติ** ใช้ได้ทุกที่เลย เพราะตัวแปรทุกตัวก็เก็บ *ข้อมูล* อยู่แล้วจริงไหม?

    ...แต่ถ้า `data` ถูกจองไปแล้วล่ะ? ก็ลองใช้ `value` แทน เป็นคำสากลเหมือนกัน เพราะสุดท้ายตัวแปรก็ต้องมี *ค่า* อยู่ดี

- **ตั้งชื่อตัวแปรตามชนิดข้อมูล: `str`, `num`...**

    ลองใช้ดู มือใหม่อาจสงสัยว่าชื่อแบบนี้มีประโยชน์อะไรกับนินจา? แน่นอน มีประโยชน์มากเลยล่ะ!

    ชื่อตัวแปรก็ยังพอบอกอะไรได้บ้าง — บอกว่าข้างในเก็บอะไร: สตริง ตัวเลข หรืออย่างอื่น แต่พอคนนอกมาอ่านโค้ด ก็จะเจอว่าชื่อแบบนี้ไม่ได้ให้ข้อมูลอะไรเลย! แก้โค้ดที่เราคิดมาอย่างดีไม่ได้สักที

    ชนิดข้อมูลหาได้ง่ายจากการดีบัก แต่ความหมายของตัวแปรล่ะ? เก็บสตริงอะไร ตัวเลขอะไรกันแน่?

    ไม่มีทางรู้เลย ถ้าไม่นั่งสมาธิให้ดี!

- **...แล้วถ้าชื่อแบบนั้นไม่เหลือแล้วล่ะ?** ก็แค่เติมตัวเลขต่อท้าย: `data1, item2, elem5`...

## ทดสอบความใส่ใจ

แค่โปรแกรมเมอร์ที่ใส่ใจจริงๆ เท่านั้นถึงจะอ่านโค้ดเราออก — แต่เราจะทดสอบยังไงล่ะ?

**วิธีหนึ่งคือใช้ชื่อตัวแปรคล้ายๆ กัน เช่น `date` กับ `data`**

สลับไปมาตามใจชอบเลย

แค่นี้ก็อ่านโค้ดผ่านๆ ไม่ได้แล้ว แถมถ้าดันมีพิมพ์ผิดอีก... อืม... คงได้ติดอยู่นาน ได้เวลาพักไปชงชากันแล้วล่ะ

## คำพ้องความหมายสุดเจ๋ง

```quote author="เล่าจื๊อ (เต๋าเต๋อจิง)"  
เต๋าที่กล่าวได้มิใช่เต๋านิรันดร์ นามที่เอ่ยได้มิใช่นามอมตะ
```

ใช้ชื่อ *คล้ายๆ กัน* กับสิ่งที่ *เหมือนๆ กัน* — ทำให้ชีวิตสนุกขึ้นและยังโชว์ความคิดสร้างสรรค์ให้คนอื่นเห็นด้วย

เช่น คำนำหน้าฟังก์ชัน — ถ้าฟังก์ชันแสดงข้อความบนจอ ให้ขึ้นต้นด้วย `display...` อย่าง `displayMessage` แล้วถ้ามีอีกฟังก์ชันที่แสดงอย่างอื่นบนจอ เช่นชื่อผู้ใช้ ก็ขึ้นต้นด้วย `show...` แทน (อย่าง `showName`)

ทำให้ดูเหมือนมีความต่างอย่างละเอียดอ่อน ทั้งที่จริงๆ แล้วไม่ได้ต่างอะไรเลย

นัดแนะกับเพื่อนนินจาในทีมได้เลย — ถ้าจอห์นใช้ `display...` ในโค้ดของเขา ปีเตอร์ก็ใช้ `render...` ส่วนแอนก็ `paint...` ดูสิว่าโค้ดจะน่าสนใจและหลากหลายขึ้นแค่ไหน

...แล้วนี่คือไม้เด็ด!

สำหรับฟังก์ชัน 2 ตัวที่ต่างกันชัดเจน — ให้ใช้คำนำหน้าเดียวกันซะเลย!

เช่น `printPage(page)` ส่งไปเครื่องพิมพ์ ส่วน `printText(text)` แสดงข้อความบนจอ — ให้คนอ่านที่ไม่คุ้นเคยได้คิดหนักกับ `printMessage` ว่า "ส่งข้อความไปไหนนะ เครื่องพิมพ์หรือบนจอ?" จะเจ๋งขึ้นไปอีกถ้า `printMessage(message)` ดันไปเปิดหน้าต่างใหม่ขึ้นมา!

## ใช้ชื่อซ้ำ

```quote author="เล่าจื๊อ (เต๋าเต๋อจิง)"
เมื่อแบ่งสรรพสิ่งออกเป็นส่วนย่อย
แต่ละส่วนล้วนต้องการชื่อเรียกขาน
นามทั้งหลายมีอยู่มากมายแล้ว
รู้จักพอคือคุณูปการอันล้ำค่า
```

อย่าเพิ่มตัวแปรใหม่ถ้าไม่จำเป็นจริงๆ

เอาชื่อเดิมมาใช้ซ้ำแทน แค่ยัดค่าใหม่ลงไปทับค่าเก่า

ในฟังก์ชัน พยายามใช้แค่ตัวแปรที่ส่งเข้ามาเป็นพารามิเตอร์เท่านั้น

วิธีนี้จะทำให้คนอ่านแทบเป็นไปไม่ได้เลยที่จะรู้ว่า *ตอนนี้* ตัวแปรเก็บอะไรอยู่ มาจากไหน เป้าหมายคือฝึกสัญชาตญาณและความจำของคนอ่านโค้ด ใครสัญชาตญาณไม่ดีก็ต้องไล่วิเคราะห์โค้ดทีละบรรทัด คอยตามการเปลี่ยนแปลงข้ามทุกสาขาของโค้ด

**ท่าขั้นสูงของวิธีนี้คือการแอบ (!) เปลี่ยนค่าเป็นอย่างอื่นที่คล้ายๆ กันระหว่างวนลูปหรือทำงานในฟังก์ชัน**

ตัวอย่างเช่น:

```js
function ninjaFunction(elem) {
  // 20 บรรทัดโค้ดที่ทำงานกับ elem 

  elem = clone(elem);

  // อีก 20 บรรทัด ตอนนี้ทำงานกับ clone ของ elem!
}
```

โปรแกรมเมอร์ที่อยากทำงานกับ `elem` ในครึ่งหลังของฟังก์ชันงงแน่... ต้องไล่ดีบักถึงจะรู้ว่าตัวเองกำลังทำงานกับตัวโคลนอยู่!

เจอแบบนี้ในโค้ดบ่อยมาก ได้ผลดีถึงตายแม้กับนินจาจอมเก๋า

## ใช้ underscore ให้สนุก

ใส่ underscore `_` และ `__` ข้างหน้าชื่อตัวแปร เช่น `_name` หรือ `__value` ถ้ามีแค่เรารู้ความหมายก็ยิ่งดี หรือดีกว่านั้น — ใส่ไปเพื่อความสนุกเฉยๆ โดยไม่มีความหมายอะไรเลยก็ได้ หรือจะให้ความหมายต่างกันในแต่ละที่ก็ดี

แค่นี้ก็ยิงปืนนัดเดียวได้นก 2 ตัว — หนึ่ง โค้ดจะยาวและอ่านยากขึ้น สอง เพื่อนนักพัฒนาจะเสียเวลาเยอะไปกับการพยายามหาว่า underscore หมายถึงอะไร

นินจาเก๋าจะวาง underscore ไว้บางที่ แล้วไม่ใส่อีกที่หนึ่ง แค่นี้ก็ยิ่งทำให้โค้ดเปราะบางและเพิ่มโอกาสเกิดบั๊กในอนาคตแล้ว

## แสดงความรัก

ให้ทุกคนได้เห็นความยิ่งใหญ่ของ entity ต่างๆ ที่เราสร้าง! ชื่ออย่าง `superElement`, `megaFrame` และ `niceItem` จะทำให้คนอ่านตาสว่างแน่

ก็จริงอยู่ว่ามีเขียนอะไรไว้บ้าง: `super..`, `mega..`, `nice..` แต่อีกแง่หนึ่งก็ไม่ได้ให้รายละเอียดอะไรเลย คนอ่านอาจต้องนั่งค้นหาความหมายที่ซ่อนอยู่ นั่งสมาธิสักชั่วโมงสองชั่วโมงในเวลางานที่ได้ค่าจ้าง

## ใช้ชื่อซ้ำกับตัวแปรด้านนอก

```quote author="กวนอินจื้อ"
ท่ามกลางแสงสว่าง มองไม่เห็นสิ่งใดในความมืด<br>
ในความมืด กลับมองเห็นทุกสิ่งในแสงสว่าง
```

ใช้ชื่อเดียวกันกับตัวแปรทั้งในและนอกฟังก์ชัน แค่นี้แหละ ไม่ต้องเสียเวลาคิดชื่อใหม่

```js
let *!*user*/!* = authenticateUser();

function render() {
  let *!*user*/!* = anotherValue();
  ...
  ...หลายบรรทัด...
  ...
  ... // <-- โปรแกรมเมอร์อยากทำงานกับ user ตรงนี้และ... 
  ...
}
```

โปรแกรมเมอร์ที่กระโดดเข้ามาใน `render` อาจไม่ทันสังเกตว่ามี `user` ตัวใหม่ในฟังก์ชันบังตัวนอกอยู่

แล้วเขาก็จะพยายามทำงานกับ `user` โดยคิดว่าเป็นตัวแปรจากภายนอก — ผลลัพธ์จาก `authenticateUser()`... กับดักวางเรียบร้อย! สวัสดี debugger...

## ผลข้างเคียงได้ทุกที่!

มีฟังก์ชันบางตัวที่ดูเหมือนไม่ได้เปลี่ยนแปลงอะไร เช่น `isReady()`, `checkPermission()`, `findTags()`... ปกติเราจะคาดหวังว่าฟังก์ชันพวกนี้แค่คำนวณ ค้นหา แล้วคืนข้อมูล ไม่ได้ไปแตะอะไรภายนอก — พูดอีกอย่างคือ ไม่มี "ผลข้างเคียง"

**กลเม็ดสุดเจ๋งคือแอบใส่การกระทำที่ "มีประโยชน์" เข้าไป นอกเหนือจากงานหลัก**

สีหน้างงๆ ของเพื่อนร่วมงานตอนเห็นฟังก์ชันชื่อ `is..`, `check..` หรือ `find...` ที่ดันไปเปลี่ยนแปลงอะไรบางอย่าง จะช่วยขยายขอบเขตแห่งปัญญาได้แน่

**อีกท่าหนึ่งที่จะสร้างความประหลาดใจคือคืนค่าผลลัพธ์แบบไม่ปกติ**

โชว์ความคิดสร้างสรรค์เลย! ให้ `checkPermission` คืนค่าไม่ใช่แค่ `true/false` แต่เป็นออบเจ็กต์ที่ซับซ้อนพร้อมผลการเช็ค

นักพัฒนาที่พยายามเขียน `if (checkPermission(..))` จะงงว่าทำไมใช้ไม่ได้ — บอกไปเลยว่า "อ่าน docs สิ!" แล้วก็ส่งลิงก์บทความนี้ให้

## ฟังก์ชันอันทรงพลัง!

```quote author="เล่าจื๊อ (เต๋าเต๋อจิง)"
มหาเต๋าไหลทั่วทุกหนแห่ง
ทั้งซ้ายขวาล้วนซึมซาบ
```

อย่าจำกัดฟังก์ชันด้วยสิ่งที่เขียนไว้ในชื่อ มองให้กว้างไกลกว่านั้น

เช่น ฟังก์ชัน `validateEmail(email)` นอกจากเช็คความถูกต้องของอีเมลแล้ว ก็อาจแสดง error แล้วขอให้กรอกอีเมลใหม่ด้วย

สิ่งที่ฟังก์ชันทำเพิ่มเติมไม่ควรเดาได้จากชื่อ นินจาตัวจริงจะทำให้มองไม่ออกจากโค้ดเช่นกัน

**การยัดหลายอย่างไว้ในฟังก์ชันเดียว จะปกป้องโค้ดของเราจากการนำไปใช้ซ้ำ**

สมมติว่ามีนักพัฒนาอีกคนแค่อยากเช็คอีเมลเฉยๆ โดยไม่ต้องแสดงข้อความ — ฟังก์ชัน `validateEmail(email)` ของเราที่ทำทั้ง 2 อย่างจะไม่เหมาะกับเขา แบบนี้เขาก็จะไม่มารบกวนสมาธิด้วยการมาถามนู่นนี่

## สรุป

"เคล็ดลับ" ข้างต้นทั้งหมดมาจากโค้ดของจริง... บางครั้งเขียนโดยนักพัฒนาผู้มากประสบการณ์ อาจมากกว่าเราด้วยซ้ำ ;)

- ทำตามบางข้อ โค้ดของเราก็จะเต็มไปด้วยเรื่องน่าประหลาดใจ
- ทำตามหลายๆ ข้อ โค้ดจะกลายเป็นของเราโดยแท้ — ไม่มีใครอยากแตะต้อง
- ทำตามทุกข้อ โค้ดของเราจะกลายเป็นบทเรียนอันล้ำค่าสำหรับนักพัฒนาหน้าใหม่ผู้แสวงหาการรู้แจ้ง
